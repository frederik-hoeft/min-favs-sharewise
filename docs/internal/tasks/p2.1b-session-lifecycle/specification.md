# P2.1b - Refresh, logout and browser session lifecycle

**Status:** Proposed architecture, requirements and acceptance tests for human review. No P2.1b behavior is implemented or approved by this document. This specification also covers the separately tracked P2.1b.1 reactive-renewal slice; neither slice is independently end-to-end complete until its backend and frontend contracts are integrated.

## Goal and boundary

A signed-in user can reload the application or open another tab without signing in again, use protected operations while the short-lived primary IAM access JWT expires, and sign out. The browser restores and renews credentials through a single frontend identity/HTTP abstraction. IAM enforces an exclusive, rotating refresh credential per durable session, detects reuse, and revokes the affected session without relying on browser cooperation.

The approved foundations are [P2.1a](../p2.1a-registration-auth/specification.md), [P2.1.0](../p2.1.0-security-foundation/specification.md), the [security design](../../../stack/security.md), [frontend architecture](../../../architecture/frontend.md), [transaction architecture](../../../architecture/transactions.md) and [test architecture](../../../architecture/tests.md). The task follows the [AI development workflow](../../../development/ai-development-workflow.md). IAM owns authentication and its `identity` tables; neither `shared` nor Group/Finance gains direct IAM persistence access. The implementation extends P2.1a's `AuthCoordinator`, `AuthSession`, `IdentityApi`, shared `lib/api` hooks and `AuthCookieLock`, rather than introducing a second HTTP client or token store.

**MVP scope:** transactional refresh rotation/replay detection, session expiry/revocation, cookie-backed logout, lazy restoration, reactive bounded renewal (P2.1b.1), cross-tab session-context detection, minimal protected-route reauthentication UX, and physical PostgreSQL/HTTP/browser verification. A scheduled token-history cleanup worker, multi-device/session administration UI, generic handler registry, cross-tab access-token sharing, and distributed cache/locks are not required. The existing database retains consumed generations so replay detection continues to work; an eventual retention/cleanup policy is separate operational work.

## Authentication state and ownership

There is **one current refresh-cookie authentication context per browser cookie jar**, not independently selectable signed-in accounts in tabs sharing that jar. Different browser profiles or private contexts have their own cookies. Each tab retains its access JWT exclusively in JavaScript memory; neither the JWT nor refresh secret is stored in React state, local/session storage, a broadcast message or a URL. The `identity.sessions.id` is a stable, non-secret session identifier for the lifetime of one login, carried as `sid` in primary JWTs. Each successful refresh creates a new opaque refresh generation **for the same session ID**. Re-login, including as the same user, creates a different session ID.

P2.1a already persists the `identity.sessions` and `identity.refresh_tokens` relation with `UNIQUE(session_id) WHERE consumed_at IS NULL`. It represents one-to-many generations **over time** and at most one unconsumed generation per session. `consumed_at IS NULL` alone does not prove a token is usable: the secret must match, and the session and account must remain eligible and within their deadlines. The existing `SessionPolicy` starts with a five-minute access lifetime, seven-day idle lifetime and thirty-day absolute lifetime. Refresh advances the idle deadline only up to the unchanged absolute deadline; any newly issued access JWT and refresh cookie are capped by the current effective session deadline.

### Server rotation and replay semantics

An IAM application operation receives the refresh cookie's token ID and secret through the HTTP adapter, validates them against its own verifier and persists the decision inside one physical PostgreSQL transaction using the existing `Transactions` boundary. No raw refresh secret is stored in the database, logged, returned in JSON, or placed in an application error. The operation obtains a stable per-session serialization lock, re-reads authoritative eligibility and token state after locking, then consumes the presented generation and inserts its successor before commit. The transaction must make the old generation's consumption, the new generation's insertion and any idle-deadline update atomic. A committed success is the only point after which the controller may release the JWT and replacement cookie.

The server verifies the **secret for the selected token ID before treating that ID as evidence of replay or revoking its family**. Unknown IDs, malformed credentials and incorrect secrets are generic authentication failures with no family mutation. A correctly authenticated *consumed* generation is reuse: it revokes its entire associated session (and hence all its refresh generations) as a committed security decision, even if a successor was issued earlier. **Replay takes precedence over an expected-session mismatch**, so a caller cannot suppress reuse detection by sending an arbitrary expected ID. The consumed-generation history must remain available for this decision. Missing, disabled, revoked or expired account/session state prohibits renewal. Replay can invalidate a recently issued successor; the browser lock prevents normal same-origin tabs from intentionally presenting the consumed cookie, but PostgreSQL remains authoritative for races from different clients or servers.

A successfully authenticated refresh belongs to exactly one session. A caller that knows its intended session presents `expectedSessionId`; if it differs from the session resolved from a **correctly verified, unconsumed** refresh credential, IAM returns a distinguishable context-change response **without consuming, rotating or revoking either session**. This comparison happens before rotation, but after the verified-replay check. A deliberate initial restoration from a fresh tab or page load may omit that binding because it has no prior tab-local session. The backend does not infer authorization from the user-supplied session ID; the refresh secret is still mandatory.

### HTTP contract

IAM extends the existing, conditionally enabled `/api/iam/v1/auth` controller and the application-owned `/api/**` Spring Security chain. The route's cookie-backed mutations inherit the existing exact-Origin and Spring CSRF checks; they do not accept a bearer token or a claimed session ID in place of the refresh cookie. **The frontend must exclude `/refresh` and `/logout` from normal bearer injection and recursive `401` recovery**, otherwise an expired access JWT would be rejected at ingress before cookie authentication could run. All credential endpoints and responses remain `no-store` and use RFC 9457 problem bodies with stable `code` values. Specific agreed wire-level outcomes are:

| Operation | Request and success | Rejection contract |
| --- | --- | --- |
| `POST /refresh` | JSON body with optional `expectedSessionId` UUID; existing secure host-only HttpOnly SameSite=Strict refresh cookie and masked CSRF request header; `200` access JWT, `tokenType`, `expiresAt`, `sessionId` and rotated `Set-Cookie` | `401 refresh_unavailable` for unknown/wrong/consumed/revoked/expired credentials; `409 session_context_changed` for a verified, unconsumed cookie bound to a different intended session |
| `POST /logout` | JSON body with optional `expectedSessionId` UUID; CSRF/Origin; revoke the authenticated cookie's session, clear refresh and CSRF cookies; `204` | `409 session_context_changed` before mutation when the valid cookie points to a different session; nonmatching/absent credentials cannot revoke a session and may only receive a generic no-op/logout failure per the HTTP test contract |
| `POST /register` and `POST /login` | Preserve P2.1a status, CSRF and cookie behavior; extend successful authentication JSON with `sessionId` | Existing P2.1a failures remain unchanged |
| `GET /csrf` | Unchanged P2.1a bootstrap under cookie lock before each credential mutation | No credential issuance or session mutation |

The exact logout handling for a missing/invalid cookie should be **idempotent `204` with a cookie-clearing response**, without pretending it revoked a different session. A verified consumed credential may cause session revocation consistent with reuse policy. The optional `expectedSessionId` is permitted only for explicitly unbound restoration/anonymous logout; a tab with a known session must send the binding. After a successful logout, the tab invalidates its bearer even if the cleared refresh cookie is already absent. A mismatched stale tab must neither clear the other tab's cookie nor revoke its session. Malformed binding values are ordinary request-validation failures with no state mutation.

The server may continue admitting a previously issued, otherwise valid **stateless access JWT** until its expiry after logout or a cookie-context switch. P2.1b changes refresh eligibility, not P2.1.0's locally verified bearer-admission rules. [P2.1d](../backlog.md#p21---iam-vertical-slices) owns optional stateful current-session eligibility checks for published consumers; immediate revocation of every outstanding access JWT is not promised here.

## Browser recovery and cross-tab consistency

The `AuthSession` stores a tab-local bearer and stable session ID. JWT expiry timestamps are display/advisory metadata; a client clock ahead of the server must not reject a valid login response or independently mark the bearer invalid. Server-verified ingress decides access-token validity. The shared HTTP client attaches the current bearer, and an identity-coordinator recovery FSM interprets **only documented pre-dispatch authentication errors** to initiate restoration/renewal. Components make ordinary API calls and do not implement token refresh, CSRF, locks or retry policies.

On a protected operation's eligible 401, the coordinator first checks whether the request used an older JWT than the tab's current one. If so, it can use the newer bearer without another rotation. Otherwise, it coalesces per-tab renewal requests into one in-flight promise, takes P2.1a's exclusive same-origin Web Lock, rechecks the current session/context, obtains a fresh CSRF token *inside the lock*, and sends one refresh POST. The lock is held until the transport settles, including abort; there is no unlocked fallback. Another tab can have rotated the cookie in the meantime and that is normal when the stable session ID agrees. After confirmed renewal, only a repeatable request known to have been rejected **before application dispatch** is replayed, **at most once**. A second 401 from the replay ends recovery; 403 and domain authorization outcomes do not cause primary-JWT refresh. Renewal entry points themselves cannot recursively invoke recovery.

The existing security chain emits `401 invalid_credential` for invalid supplied JWTs and `401 authentication_required` for protected, missing credentials before dispatch. These are the starting positive allowlist for safe bearer recovery; `401 unauthenticated` from inside an operation is **not** automatically replayable. The implementation must verify the exact response/ingress contract in tests before enabling retries of POST/PUT/PATCH/DELETE requests, and reject non-replayable bodies. Unexpected 401s, malformed error responses and failed replay preconditions propagate an authentication error rather than guessing that the operation did not run. A small bounded cooldown may suppress repeated independent recovery attempts after a terminal failure; it must not prolong retries of a consumed refresh credential. Backoff is not a license for repeated refresh-token mutation.

When a tab has no local bearer and its identity is first needed (including reloading the current demonstration workspace), the coordinator attempts one **unbound lazy restoration** through the same locked refresh workflow and then uses the returned JWT. After restoration, every subsequent renewal and logout is session-bound. An absent/invalid refresh cookie results in a typed reauthentication-required state; the application navigation boundary, not the transport, redirects genuinely protected pages to `/auth/login?next=<path>`. `next` preserves a validated same-origin **page path** and never replays a pending write after login. Public-page API callers may handle the typed terminal error without forced navigation. The illustrative workspace itself is not silently promoted to a protected product route; route protection is applied to actual authenticated experiences.

`BroadcastChannel` carries **only non-secret login/logout/session-context-change notifications** (including the stable session ID when useful). On a login/switch notice identifying a different session, a tab with an established session suspends protected actions and shows a minimal "sign-in changed" prompt. On logout, only tabs bound to the revoked session invalidate their local authentication; unrelated sessions ignore that event. Reloading explicitly discards stale tab-local state and restores the browser's **current** cookie context. Session changes can be missed by suspended tabs; the authoritative `expectedSessionId` check catches them on later refresh/logout. Notifications never install another tab's JWT, rotate cookies, or authorize a request. Same-session rotations do not trigger account-change prompts. Out-of-order notifications must never silently adopt another session or cause destructive cookie mutation.

### Recovery uncertainty and validation-endpoint decision

An outbound refresh request whose result is unknown (timeout/network interruption, truncated success body, or unexpected response after possible commit) **must not be retried with the same cookie**. The server may have committed consumption and rotated the cookie while the browser did not receive the replacement `Set-Cookie`; a second submission could trigger valid replay protection and revoke the session. The coordinator enters a terminal recovery-uncertain state, invalidates its bearer for authenticated workflows, and offers reauthentication. Clear the browser's refresh cookie only as part of an explicitly reviewed local sign-out/reauthentication transition, not by sending a second potentially destructive logout or refresh POST. If another tab has already authenticated to a different session, preserve that tab's cookie and use the context-change UX.

A future authoritative **access-JWT/session eligibility endpoint** can report whether an already-held bearer is presently accepted, but **cannot establish whether a refresh transaction committed or whether the browser holds its replacement HttpOnly cookie**. A successful bearer validation is therefore insufficient to resolve this ambiguous cookie-generation state. P2.1d's published eligibility capability and optional private remote introspection remain deferred. A distinct read-only *active refresh-cookie* status protocol could be considered later if reauthentication frequency warrants it; it would require its own authenticated-cookie, CSRF, response-race and retention design, and is not a prerequisite for safe MVP behavior.

## Requirements and invariants

| ID | Requirement / invariant |
| --- | --- |
| IAM-B01 | Each refresh credential has a 32-byte secret verifier, is bound to exactly one durable IAM session, and only the verifier/hash and history metadata are persisted. No secret is exposed in JSON or diagnostics. |
| IAM-B02 | At most one unconsumed refresh generation per session; rotation and idle extension commit atomically under PostgreSQL per-session serialization, without an outcome visible before commit. |
| IAM-B03 | Invalid/missing/wrong-secret token selectors never revoke a session; correctly verified consumed-token reuse revokes the session family and prohibits successor renewal. |
| IAM-B04 | Disabled, revoked, idle-expired and absolute-expired sessions cannot renew. Idle extension never moves the absolute deadline; access JWT and cookie validity stay capped. |
| IAM-B05 | Bound refresh/logout rejects a different valid cookie session without consuming, revoking or clearing it. New-context restoration is explicitly unbound; the browser never silently switches an established tab. |
| IAM-B06 | Refresh/logout retain P2.1a CSRF, strict Origin, secure cookie and no-store properties, and do not send stale access bearers. Logout is effectively idempotent and never revokes a different session. |
| IAM-B07 | The frontend uses only tab-memory JWTs, one shared API client and lock-protected cookie mutation. Server response governs expiry; clock skew does not autonomously discard a successfully issued JWT. |
| IAM-B08 | One in-tab refresh flight, cross-tab Web Lock and at most one safe original-request retry; no retry loops, mutation replay after dispatch, or replay of an uncertain refresh POST. |
| IAM-B09 | Cross-tab session changes surface a prompt while same-session rotation stays transparent; missed notifications are caught by server-side session binding. |
| IAM-B10 | Lazy authenticated-route restoration and typed terminal recovery expose a validated same-origin login return path, without replaying a business mutation. |
| IAM-B11 | No changes to P2.1.0 issuer/audience/type verification, published `IdentityContext`, Group/Finance policy or immediate invalidation semantics of outstanding stateless access JWTs. |

## Central test and acceptance design

These scenarios specify observable correctness; implementation phases add component-level regression tests. Real PostgreSQL tests are mandatory for row locking, unique indexes, transaction commit and cross-connection races. Browser tests are mandatory for actual HttpOnly cookies, Web Locks and navigation.

| ID | Level | Setup/action | Required observation |
| --- | --- | --- | --- |
| IAM-BT01 | Unit + PostgreSQL E2E | Refresh using the current valid cookie | One old generation consumed, exactly one new unconsumed generation, same session `sid`, bounded idle/cookie/access expiry; response only after commit |
| IAM-BT02 | PostgreSQL E2E | Two concurrent refreshes present the same valid generation on independent connections | Exactly one rotation winner; later verified reuse revokes the family; no two active generations, rollback anomalies or partial issuance |
| IAM-BT03 | Unit + PostgreSQL E2E | Unknown ID, malformed token, wrong 32-byte secret or correct ID with wrong verifier | Generic failure with no session revocation, generation change or token-oracle leakage |
| IAM-BT04 | PostgreSQL E2E | Reuse a correctly verified consumed generation after successful rotation, including with a deliberately mismatched `expectedSessionId` | Session revoked durably despite caller-supplied binding; previously issued successor can no longer renew |
| IAM-BT05 | Unit + PostgreSQL E2E | Refresh around idle/absolute boundaries, disabled/revoked user/session, induced insert/commit failure | Expired/ineligible denied; idle bounded; rollback preserves prior generation and never exposes committed-looking credentials |
| IAM-BT06 | HTTP E2E | Valid logout, repeated/missing-cookie logout, logout racing with refresh, and logout with a different expected session | Same-session revoked and cookies cleared; no cross-session revocation or cookie clearing on mismatch |
| IAM-BT07 | HTTP E2E | Refresh/logout without CSRF or Origin, with wrong/multiple Origin, or blocked cookie context; separately try invalid bearer on normal API | Existing security chain enforces CSRF/Origin before mutation; refresh/logout use cookies without an access bearer, and cookie alone cannot authenticate bearer-only APIs |
| IAM-BT08 | Frontend Unit + HTTP | Clock ahead/behind server; initial success with `expiresAt` in the local past; protected 401/403/pre-dispatch codes | Client retains valid server-issued bearer, renews only eligible 401, never treats 403 as renewable |
| IAM-BT09 | Frontend Unit + browser | Same tab sends parallel protected requests; two tabs independently need renewal | Single-flight + exclusive Web Lock prevent self-replay; both tabs continue with same `sid` and current cookie |
| IAM-BT10 | Frontend Unit + browser | Tab A logged in as S1; Tab B logs in as S2 (also test same user, new session); A receives/misses a broadcast | A does not use S2 as S1, sees context-changed prompt proactively or on refresh; S2 cookie/session untouched |
| IAM-BT11 | Frontend Unit + browser | Reload demo workspace/new tab with a valid cookie; simulate a genuinely protected route and expired bearer, then refresh fails | Silent restoration when cookie valid; typed reauthentication and safe `next` redirect for protected routes otherwise; no body mutation replay |
| IAM-BT12 | Frontend Unit + HTTP | Refresh response lost/aborted after commit or malformed after `Set-Cookie`, repeated 401, unreadable body, missing Web Locks | No second uncertain refresh submission, no unbounded retries, fail-closed UI; lock not released before request settles |
| IAM-BT13 | HTTP + frontend Unit | Protected GET and replayable POST rejected by bearer ingress before dispatch; operation-generated 401 and non-replayable body | Only explicit pre-dispatch errors retry once, with no duplicate business side effect; other cases propagate |
| IAM-BT14 | Human HTTPS browser | Register/login, reload, multiple tabs, stale-context prompt, logout in one tab, expired JWT, invalidated cookie | Navigation and UI recovery work without credential leakage; no silent account switch; check relevant cookies by attributes only |

## Deferrals and review gates

Scheduled deletion of consumed/expired refresh records, a durable retention policy for consumed generations, session/device administration, cross-instance deployment chaos testing, proactive token refresh timers, independent password-change/session invalidation UX (P2.1c), authoritative IAM state lookups (P2.1d), and Group attestations (P2.5) remain separate work. **Database concurrency correctness across independent connections remains mandatory**, even though a multi-node deployment rehearsal can be deferred.

The human approves this specification and its test contract first, then separately approves the [implementation plan](plan.md). Both approved documents must be committed to the authoritative task branch before implementation. Each implementation phase returns a focused patch for review. Independent security review, PostgreSQL E2E, frontend CI and human HTTPS browser acceptance precede the final merge decision. If the proposed refresh error/retry contract needs a material architectural change, return to the specification gate before proceeding.
