# ShareWise implementation backlog

**Status:** Active implementation roadmap. Phases are ordered by technical and functional dependencies, **not** by calendar sprints or team capacity. Each phase is a reviewable milestone that may be decomposed into smaller requirements/plan/implementation patches. Completion requires the listed acceptance gate, review, and an update to the authoritative documentation.

The existing [architecture](../../architecture.md) and [domain model](../../data-model-design.md) define the intended boundaries, domain language, transaction model, and invariants. This backlog schedules work against those contracts; it is **not** a replacement for them.

## Working agreement

- Implement a **modular monolith first**. Preserve the five contexts and their data ownership without introducing five processes, an early message broker, or an application-wide shared domain model.
- Deliver **vertical business slices**: API, application service, domain logic, persistence adapter, authorization, relevant UI, and tests belong to the same feature milestone where feasible. Platform foundations are separated only when several slices genuinely depend on them.
- Design and review each phase before coding. Record detailed task requirements and plans under `docs/internal/tasks/<task>/` as appropriate, including decisions, invariants, failure semantics, interface contracts, tests, and reviewable subpatches.
- Prefer ports for real external or persistence boundaries, not interfaces for every Java class. Keep SQL/JPA entities private to adapters; expose immutable, operation-focused contracts.
- All financial mutations must preserve group-local ordering, atomic journal/revision updates and historical consistency. Tests against real PostgreSQL are required for database semantics.
- Only check tasks off when their acceptance evidence exists. Design questions are not implicitly answered by an implementation convenience. Scope changes update the relevant architecture/domain docs.
- Prefer small **task-scoped** feature branches and frequent reviewed merges to reduce lead time. Keep work independently understandable and transfer-ready: if a dependency owner is unavailable, another contributor may take over the bounded task after brief coordination, without weakening its review and test gates.

Framework introductions that modify the Maven POM or npm lockfile require **refreshing and revalidating** the separately supplied offline dependency handoff. Do not substitute uncached dependencies or change versions to mask an incomplete handoff. The initial rename also changes manifest paths and the POM hash; an old verifier cannot validate the renamed tree unchanged, even if offline compilation succeeds with its dependency cache.

## Phase 2 - Identity and group membership vertical slices

**Depends on:** The applicable Phase 1 foundations and the approved P0.2 security flow. P2.0 contract work can proceed before PostgreSQL provisioning; persistence and database-specific acceptance for the vertical slices require P1.2 and the relevant P1.3/P1.5 test infrastructure.

**Delivery model:** P2.0 establishes the smallest shared, reviewable contracts and frontend foundations needed for independent feature work. P2.6 provides an early, independently developed deployment path instead of postponing containerization and CI/CD to Phase 8. P2.1 and P2.2 are **vertical slices**: each owns its relevant application behavior, persistence, HTTP adapter, frontend journey and tests, rather than handing off a backend-only feature to a separate frontend epic. Implementations can initially use contract-conforming test doubles at neighboring module or HTTP boundaries; final acceptance integrates the real providers and verifies their database/security behavior. Task identifiers below describe the initial decomposition, not yet approved specifications or implementation plans. Detail, edge cases and subphase gates are settled through the [AI development workflow](../../development/ai-development-workflow.md).

Initially allow only identities present in the local projection; reject a missing user (interim `403`, with no JWT refresh retry), including registration-to-join replication lag. Prove duplicate delivery, consumer rollback, registry retry/recovery and initial population for users registered before the subscriber. Apply `UserDeleted` only after P2.1e's deletion policy is approved; event ordering must not permit an old registration to recreate a deleted identity. Do not introduce a generic inbox if a proven projection invariant is sufficient.
- [ ] **P2.2e - Authoritative IAM lookup on local miss:** After P2.1d and P2.2d, resolve an authenticated user missing from `groups.users` through IAM's published Java current-state verification capability, not merely JWT signature verification. An eligible authoritative result permits local projection provisioning and the Group operation; deleted/disabled/invalid sessions are rejected, and lookup failures fail closed without misclassifying outages as absent identities. Use the verified caller identity, not a caller-selected UUID. Check concurrency with deletion/event consumption and prevent late events from undoing authoritative deletion. Known active local identities retain the documented bounded JWT/event staleness until an explicitly stronger policy is approved; do not add an IAM call to every Group request.

### P2.4 - Durable cross-context event integration

- [ ] **P2.4a - First durable integration: IAM → Group user projection:** Coordinate with the real Group consumer in P2.2d (neither task independently proves the end-to-end delivery guarantee); define stable, versioned IAM user-registration event contracts and the initial Spring Modulith JDBC publication-registry migration/configuration (Flyway-owned, shared datasource/transaction, no custom outbox or broker). Publish registration facts with the IAM commit; consume them in an independently committed Group operation. Test real PostgreSQL commit/rollback atomicity, independent consumer commit and registry `DELETE` completion, duplicate/reordered delivery, failure/recovery, listener identity and retention. Coordinate producer/listener deployment and bootstrap of pre-existing IAM users: the registry cannot replay registration events from before a listener was registered. Reserve an account-deletion event contract for P2.1e, whose deletion and ordering semantics must be approved before publication/consumption. Keep the infrastructure reusable for later membership events without building a speculative messaging framework.
- [ ] **P2.4b - Group authority and membership-event publication:** Establish the published membership/permission projections and operations needed by Group consumers such as Finance and attestation issuance; agree on role and invitation boundary semantics. Define stable, versioned Group-created and full-state membership-change event identities/payloads, with **transactionally assigned group-local membership source revisions** for member events, following [the messaging architecture](../../stack/messaging.md) and the [proposed P3.0 Finance integration contract](../integration/phase-3-foundation.md). Coordinate this source contract with P3.0 before selecting the Group schema/producer representation; Finance consumes the source versions but does not own them. Publish separate `GroupCreatedV1(eventId,groupId)` and initial-owner `GroupMemberAddedV1(revision=1)` facts with the same atomic Group/owner creation transaction **when the real Finance subscribers are registered**; publish later add/remove facts with the committed incremented Group membership revision, reusing P2.4a's registry and proven listener/producer pattern. Test event identity, commit/rollback, transaction boundaries and recovery; do not register unused consumers.
- [ ] **P2.4c - First membership consumer and delivery acceptance:** Integrate the first membership consumer (initially expected to be **P3.2 FinancialActor synchronization**) with independently owned operation transactions, idempotency, out-of-order handling and registry completion. Test replay, failure/recovery, unknown-member tombstones and either delivery order of the independently published GroupCreated and initial-owner membership facts on real PostgreSQL. Coordinate this task with P3.2 rather than implementing an unused mock subscriber to declare P2.4 complete.

**IAM → Group sequence:** Group Management first runs against closed-world `groups.users` fixtures (P2.2a–c), independent of IAM implementation. P2.4a/P2.2d introduce durable **event-only** replication with a documented temporary rejection on local misses. P2.1d adds authoritative IAM verification using the P2.1.0 JWT/JOSE foundation (not the later P2.5b Group attestation flow); P2.2e adds the synchronous **lookup only on misses** to remove registration-lag rejection. IAM and Group verticals can proceed in parallel until their integration gates. Permanent deletion and its effects on Group invariants require P2.1e's separate policy gate.

### P2.5 - Group attestations and downstream authorization

- [ ] **P2.5a - Group attestation verification and authorization policies:** Extend P2.1.0's shared claims infrastructure with an operation-scoped provider for Group-issued attestations and reviewed, domain-specific policy services. Providers validate signature, issuer, audience, token type, lifetime and structural claims; policies correlate the attestation with the verified primary IAM issuer, subject and session, then enforce resource- and operation-scoped permissions. Verify cross-token identity/session binding before attestation claims are exposed to application consumers, and never combine unrelated Group claim sets into one grant. Define test attestation fixtures and prove mismatch, expiry, wrong issuer/audience/type, missing primary identity, cross-group role confusion and multiple-credential isolation before accepting downstream consumers. No Group business operation should authorize its own state mutations from a previously issued attestation; authoritative membership checks remain Group-owned. This task does not duplicate P2.1.0's JOSE/operation-scope foundation or introduce a general policy engine.
- [ ] **P2.5b - Group attestation vertical:** Issue short-lived, IAM-session-bound Group Management attestations only after authoritative role/membership checks; integrate the protected group/resource operation flow and the frontend's attestation acquisition/renewal as needed. Use P2.5a's verified, provenance-preserving Group attestation provider and domain-specific policies so consumers do not interpret raw claim names or combine unrelated attestations. Test identity/session mismatch, wrong issuer/audience/type, cross-group privilege confusion, refusal to issue new privileges after role downgrade, bounded validity of outstanding attestations, `401` renewal versus `403` denial, and key rotation. Preserve each consuming context's own authorization/business checks; Group Management continues to authorize its own mutations from live state, and optional distributed introspection remains deferred by [the security design](../../stack/security.md).

### P2.6 - Production packaging, deployment and CI/CD

**Purpose:** Make the modular-monolith application deployable early, independently of the completion of all business verticals. This epic moves the initial production container/Nginx, GitLab image CI and deployment responsibilities from Phase 8 into Phase 2. It can proceed in parallel with IAM and Group Management once the necessary build/runtime interfaces are available; it does not own their application logic or P8's later operational hardening.

- [x] **P2.6a - Production images and Compose stack:** Define reproducible, lean production Dockerfiles for the Spring backend and statically exported Next.js frontend, with Nginx serving assets, terminating TLS and proxying same-origin `/api/*` traffic. Define Docker Compose services/networks for Nginx/frontend, backend and PostgreSQL, including persistent database storage, Flyway startup/migration ordering, health checks, internal-only backend/database exposure, proxy headers/cookie behavior and environment/secret injection. Preserve the single-modulith deployment and validate a clean local production-style Compose startup.
- [x] **P2.6b - GitLab CI image publishing and versioning:** Extend existing build/test/lint jobs with reproducible production-image builds and authenticated pushes to **GitLab Container Registry** (separate image paths per deployable). Use `MAJOR_VERSION.MINOR_VERSION.CI_PIPELINE_IID`: publish stable versions from protected `main` pushes and opt-in prereleases with the `-<slug>` suffix from protected `dev-<slug>` Git tags. Ordinary feature branches and merge requests do not publish. Promote the mutable `latest` aliases only from protected `main`, and retain paired digest-qualified image references for deployment/rollback rather than assuming version tags cannot be overwritten. Evaluate a custom Docker-capable runner versus **daemonless builds on the provided runners**: the example uses Kaniko, but verify a maintained executor image or alternatives such as BuildKit/Buildah rather than assuming the archived upstream Kaniko image remains suitable. **Do not require Docker-in-Docker, a host Docker socket or privileged mode on the university runners.** Test registry authentication, tagging and image publication on the actual GitLab runner.
- [ ] **P2.6c - Proxmox deployment hosts:** Provision a **production VM**, with a **staging VM optional** if it adds useful acceptance coverage. Set up the container runtime/Compose, persistent volumes, TLS/DNS, firewall and administrative access, GitLab registry pull credentials, secret provisioning and least-privilege service/network exposure. Document reproducible host bootstrap and application configuration; agree on secure administrative access without making an individual's VPN or workstation a mandatory production dependency.
- [ ] **P2.6d - GitOps or scripted deployment:** Evaluate [Doco-CD](https://doco.cd/latest/) for Compose-based deployments on the Proxmox host(s), including GitLab integration, polling/webhooks, image-tag/digest promotion, registry access, privileged Docker-host control, secret handling, drift/recovery and rollbacks. **If viable**, install and configure it on production (and staging when present); ensure image publication is followed by an explicit desired-state/image-version update, since pushing a registry tag alone does not update a Git-tracked Compose deployment. Otherwise deliver an idempotent, documented deploy/update/rollback script with equivalent low-friction execution. Verify deployment, upgrade, failure visibility and rollback on the provisioned host.

**P2.6 gate:** GitLab CI builds and tests the applicable applications, produces versioned production images and pushes them to the GitLab Container Registry using a runner-compatible builder; a clean provisioned production host can pull the images and start the Compose stack with Nginx and PostgreSQL. A new version can be deployed **automatically through a validated GitOps flow or reliably through a documented, hassle-free script**, with secrets excluded from the repository, a health/smoke check and a tested rollback path. Staging is optional. This is deployment-enablement acceptance, not the later complete MVP journey and observability gate in P8.

**Numbering:** The former **P2.3 frontend-only epic is retired**. Its authentication/session UI and browser concurrency requirements are assigned to P2.1, group/member/invitation UI to P2.2, attestation UX to P2.5b, and shared frontend design/tooling to P2.0e. This avoids a cross-team frontend handoff while retaining traceability to the prior backlog.

**Phase 2 gate:** An authenticated user can register, log in, renew/logout securely, create a group, invite another user and manage organizational membership end to end through real API and frontend flows, including an immediately following group operation before registration-event delivery via the authoritative local-miss fallback. Verify token/session/CSRF and authority-scoped access, denial and race scenarios, plus final-member/final-administrator constraints against PostgreSQL and suitable browser integration tests. Demonstrate IAM → Group durable publication, event consumer idempotency/recovery, and current-state fallback with real PostgreSQL; document any explicitly deferred permanent account-deletion policy. Initial container/registry/deployment acceptance is established independently under P2.6; durable membership delivery is accepted with its first consumer under P2.4c/P3.2, not inferred from Phase 2 UI acceptance.

## Phase 3 - Finance actor synchronization and accounting foundations

**Purpose:** Establish the two-table Finance aggregate, versioned Group membership projection, pure accounting primitives, and group-local financial revision coordination. The [Phase 3 foundation](../integration/phase-3-foundation.md) is the **single shared architectural/integration contract**, including column provenance, event and lifecycle semantics, concurrency, failure behavior and cross-team acceptance scenarios. This backlog owns **work sequencing, task deliverables and gates**; individual tasks define their own detailed specifications and implementation plans under the [AI development workflow](../../development/ai-development-workflow.md).

### P3.0 - Shared contract review gate

- [ ] **P3.0 - Approve the Phase 3 foundation:** Human review of the [technical ER and cross-team handoff](../integration/phase-3-foundation.md), including the two Finance tables, Group-side source revision, independent `GroupCreatedV1` and initial-owner membership events, actor-local ordering and lifecycle/replication separation. Confirm Group-attestation versus actor eligibility, one implicit fixed two-decimal MVP denomination, delivery/recovery assumptions, and deferral of Group deletion, existing-Group runtime backfill and periodic reconciliation. Review the shared cross-team test scenarios and ownership/dependencies below. **This is a design-only gate:** no migration, subscriber or service is implemented by P3.0.

### Execution order and parallel work

| Lane | Prerequisites / blocker | Independent deliverable and integration point |
| --- | --- | --- |
| **P2.4b Group producer** | P3.0 event/revision contract; P2.4a registry for real publication | Group-owned revision and two independent creation facts; event DTOs can be agreed while Finance schema is built. |
| **P3.1a Finance schema** | P3.0 approval + P1 persistence foundation | **Sole owner of first Finance migration**; unblocks both root provisioning and revision work. Parallel with P2.4b and P3.3. |
| **P3.1b Root and lock** | P3.1a; agreed Finance operation contract | Idempotent root/lock primitive; required for live P3.2a operation tests and financial write coordination. |
| **P3.2a Projection core** | P3.1a and P3.1b operation contract/implementation | Group-created activation and guarded membership transitions, independently testable with event fixtures before P2.4b completes. |
| **P3.2b Event integration** | P3.2a + P2.4a registry + P2.4b published DTOs | Real Finance consumer; **P2.4c joint PostgreSQL E2E** is the acceptance boundary for producer-to-consumer delivery. |
| **P3.3 Accounting** | P3.0 fixed-unit/rounding contract only | Pure Java, no schema, events, Group or P3.1/P3.2 blocker. |
| **P3.4 Financial revision** | P3.1a + P1 transaction foundation + agreed P3.1b lock contract | Financial write coordination can be designed in parallel with projection; PostgreSQL acceptance needs the shared root/lock implementation, not delivered actor events. |

Each lane may develop and unit-test against approved contracts/fixtures before its provider's live implementation is ready. **Only the named owners may change shared schema or event contracts**; changes that alter a cross-team contract return to the P3.0 review gate. Unit tests or mocks cannot establish database locks, Flyway behavior or registry recovery; the integration owners coordinate real PostgreSQL acceptance. No Phase 3 lane should block on P2.5 attestation issuance: authorized Finance API enforcement belongs to the later API verticals.

### Independently owned tasks

- [ ] **P3.1 - FinancialGroup and FinancialActor persistence/provisioning:**
    - [ ] **P3.1a - Finance schema:** Create `finance.groups` (`id`, `state`, `current_revision`, `created_at`) and `finance.actors` (composite `(group_id,user_id)` PK, Finance-local FK, `deleted`, positive `upstream_revision`, timestamps/update trigger) using the types/constraints in the [foundation](../integration/phase-3-foundation.md#p3-schema-reference-financegroups). No currency, external FK or journal. Verify Flyway DDL, constraints, type defaults and orphan-actor rejection against PostgreSQL.
    - [ ] **P3.1b - Idempotent root provisioning and lock:** Provide a shared Finance-owned insert-if-absent/row-lock operation for the first trusted Group event, `provisioning` lifecycle and typed not-ready behavior. Verify concurrent first inserts, isolation between groups, and rollback on PostgreSQL. Do not also implement the Group event listener.
- [ ] **P3.2 - Retained, source-versioned FinancialActor projection:**
    - [ ] **P3.2a - Finance projection operations:** Apply full-state member changes with per-actor `upstream_revision` guards, including unknown-removal tombstones and stale-event no-UPDATE behavior; separately activate `provisioning → open` on `GroupCreatedV1` without creating an owner. Use the shared root lock, leave `current_revision` untouched and detect contradictory same-revision facts. Test concurrent/duplicate/reordered events, ABA, owner-late and timestamp behavior on PostgreSQL.
    - [ ] **P3.2b - Durable consumer wiring:** Connect these operations to P2.4a/b's registered events. With **P2.4c**, verify independent initial-owner/Group-created facts arriving in either order, later member events arriving first, real source/consumer transaction boundaries, registry completion failure, redelivery and recovery on PostgreSQL. No separate Finance queue, initial snapshot callback or periodic scheduler.
- [ ] **P3.3 - Fixed-unit accounting algorithms:** Implement exact Money/Percentage and equal/fixed/percentage splits with one fixed two-decimal denomination. Verify nonpositive/overflow/invalid precision, input-order-independent remainder distribution and conservation using Unit/property tests; no database or messaging prerequisite. Select and document the concrete display currency **before P4 money writes are available**.
- [ ] **P3.4 - Financial revision coordination:** Use the same Finance root lock for serialized, group-scoped financial revision allocation. PostgreSQL tests cover concurrent commits, rollback without committed gaps, overflow and independent groups. Membership projection and creation activation do not allocate a financial revision. P4/P5 own subsequent ChangeRecord, expense and settlement persistence.

**MVP rollout:** Register the real Finance listener before creating Group data whose events must replicate. Pre-existing disposable Groups are reset/reseeded at deployment or backfilled by a **separately approved, writes-suspended Flyway release migration**, not by a P3 runtime job; publication obligations do not exist retroactively. Incomplete deliveries rely on P2.4a's publication registry and its recovery mechanism. Snapshot-based drift repair and scheduled retry are conditional [P8.4 hardening](#phase-8---operational-hardening-and-full-mvp-readiness), not Phase 3 blockers. Group deletion and safe terminal retention/replay behavior require a later policy gate and **are not implemented** in P3.

**Phase 3 acceptance gate:** P3.1 migrations/locks, P3.2 consumer behavior, P2.4c cross-context delivery, P3.3 pure calculations and P3.4 financial revision atomicity have their documented Unit/PostgreSQL Integration/E2E evidence as applicable. The **P3-applicable** [foundation integration scenarios](../integration/phase-3-foundation.md#integration-scenarios-that-require-coordination) must hold; attestation-protected Finance API read/write acceptance is deliberately deferred to P4/P5, not a P3 dependency. Actor replication is never an authorization source and `open` is not proof of projection freshness. Human approval and task-level reviews are required before checking any work complete.

**Depends on:** Phase 3 finance foundations.

- [ ] **P4.1:** Create expenses with payer, participants, strategy and stored allocation shares, enforcing group/actor eligibility and authorized authorship policy.

## Phase 5 - Settlements and financial lifecycle vertical slice

- [ ] **P5.3:** Implement `OPEN → CLOSED`, `CLOSED → OPEN`, and terminal `ARCHIVED` as ordered financial operations with journal entries and Finance-owned lifecycle checks. - [ ] **P5.4:** Add settlement, close/reopen/archive and historical-revision frontend views.

**Gate:** A full Mallorca-style journey works end to end. Closed groups reject expense edits while allowing settlements; archived groups are read-only; any past group revision yields reproducible balances.

**Depends on:** Observable modulith behavior and a concrete change driver; not automatic because a lecture reaches the microservices topic.

## Cross-cutting review checks

For **every** implementation patch: verify the affected public contracts and exact domain invariants; include focused failure/concurrency tests, run applicable build/lint checks, update `docs/` to describe the current steady state, and record remaining environmental gaps. Keep the current approved baseline intact until review.

**Deferred, not forgotten:** explicit per-group currency storage/selection (MVP has one fixed implicit unit), currency conversion, inactive-actor eligibility, expense authorship and settlement authority, attachment history, deletion/retention, notification template/channel history, and distributed file authorization. Their authoritative tracking location is the [domain model's open decisions](../../data-model-design.md#open-decisions); resolve each before its dependent feature phase, not by assuming a database shape.
