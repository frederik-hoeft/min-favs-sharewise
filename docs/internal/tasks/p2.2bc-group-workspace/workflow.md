# Task-local workflow pilot

**Status:** Proposed task-local instructions for maintainer approval. Applies only to P2.2b/c. The [AI development workflow](../../../development/ai-development-workflow.md), [ChatGPT development guide](../../../development/chatgpt-development-workflow.md), root `AGENTS.md` and repository skills remain authoritative except for the explicitly approved intermediate-gate substitution below.

## Approval and phase discipline

The maintainer approves the [specification](specification.md) and then the single [plan](plan.md) before dependent implementation. Commit and provide the approved task documents for application/push to the authoritative task branch before proceeding; a local CaaS commit is not an upstream push. Preserve the supplied P2.2a baseline on `main` and use a dedicated feature branch. Do not merge into the approved baseline without final authorization.

The pilot delegates routine intermediate implementation review to the implementation agent, not the final acceptance decision. Work phase-by-phase in the same implementation turn where execution permits; do not stop for routine intermediate approval. The mandatory exceptions are the jOOQ handoff, pre-documentation human feedback, and material architecture/scope revisions or a blocker that prevents safe progress. Do not proceed past a known correctness defect or fabricate unavailable validation. Human acceptance, independent PR review and final merge authorization remain unchanged.

Before **every** implementation phase, manually open and re-read the complete [engineering-quality skill](../../../../.agents/skills/engineering-quality/SKILL.md), even if loaded earlier. Read applicable documentation skill, review checklist, route-local instructions and technical references when relevant. Record phase-specific requirements/tests, implement focused changes, then run the strongest relevant available checks. Validate real persistence semantics with real database tests; mocks only prove their own boundary. Keep repository source independent of the offline environment; never change dependencies or generated schema merely to bypass missing tooling.

Before closing each phase, deliberately review the complete phase diff and affected feature-branch call paths against specification and engineering guidelines. Scrutinize authorization, state/transaction boundaries, failure and concurrency behavior, reuse, test strength, unnecessary complexity and accidental changes. For substantial UI work render the running application through browser CDP with a mock REST boundary outside production source, inspect screenshots at wide/intermediate/mobile sizes and light/dark themes, and correct issues. Record concrete findings and follow-up corrections; rerun affected checks and review iteratively until no known substantive issues remain. Self-review is not an independent review or human acceptance.

## Checkpoints and recovery

After phase review and validation, update the plan with evidence, commit the phase with `P<task id>-<phase>: <message>`, and generate a binary-capable incremental Git patch relative to the preceding published checkpoint (including task-doc updates). Verify clean application and resulting tree against the predecessor, record predecessor/resulting tree IDs and SHA-256 digest, and expose the exact file through a user-visible download link before continuing. Prefer a format-patch for replayable commit metadata or a verified `git diff --binary` with recorded commit message. Do not publish cumulative patches as if they were incremental. Do not expose secrets, local toolchains or generated build artifacts. The original archive plus patches in order must restore the same source tree; local merge commits are not required for this recovery. Keep the original `main` unchanged; checkpoints are self-reviewed feature-branch commits, not human-approved merges.

If the execution environment resets, restore the exact original archive, replay published patches in sequence, verify hashes/tree and resume from the last completed checkpoint. Do not approximate lost changes from memory. If a turn must stop unexpectedly, distinguish completed published checkpoints from unfinished work; do not imply work runs asynchronously.

## Mandatory human gates

1. **Code generation:** publish all completed patches through the invitation migration phase, then stop. The maintainer applies them on the authoritative branch, reviews progress, migrates PostgreSQL, generates Group jOOQ sources and returns the generated diff. CI schema freshness is expected to fail while the migration is present without generated sources; that is a documented intermediate state, not a waived final gate. Apply and verify the returned patch as a distinct checkpoint before writing code requiring new generated types. Resume after maintainer feedback. No handwritten generated schema or disabled freshness test.
2. **Pre-documentation:** publish all reviewed implementation patches and the aggregate change/validation summary. The maintainer performs real PostgreSQL suites, schema freshness, CI, production smoke, manual acceptance and aggregate review, then provides feedback. Address confirmed findings with incremental patches and rerun relevant checks. Only reconcile steady-state docs once implementation behavior is accepted; record any remaining exceptions explicitly.
3. **Final:** independent PR reviewers examine the same integrated revision and findings are resolved or justified. Reconcile docs after behavior changes and rerun affected tests. Maintainer authorizes merge and backlog completion. No self-review claim substitutes for this gate.
