# P1.2 – PostgreSQL and migration foundation

**Status:** Draft specification for team review. Covers the open P0.3 database-contract decisions required by P1.2 and the P1.2 implementation scope. Nothing in this document is implemented yet. Decisions marked **(proposal)** require team approval before the implementation plan is written.

**Related documents:** [persistence architecture](../../../stack/persistence.md), [application architecture](../../../architecture.md), [development guide](../../../development.md), [backlog](../backlog.md) (P0.3, P1.2).

## Goal

ShareWise replaces the starter's H2 database with **PostgreSQL** as its authoritative store. **Flyway** SQL migrations define the schema, each bounded context owns a dedicated PostgreSQL schema, and every developer, test run and CI job uses the same PostgreSQL major version. Unit tests stay database-independent; integration tests run against real PostgreSQL. The result is the persistence foundation on which P1.3 (transactions) and the first feature slices build.

## Architectural solution

### Database and runtime topology

| Environment | PostgreSQL provisioning | Configuration source |
| --- | --- | --- |
| Dev container | `postgres` service in `.devcontainer/docker-compose.yml`, named data volume, health check | Default datasource settings for the dev container |
| Integration tests | Testcontainers PostgreSQL by default; an externally supplied JDBC URL is accepted (CI service, local compose database) | Test fixture |
| CI | GitLab job with Docker-capable runner **or** a `postgres` CI service (see open question Q2) | CI variables |
| Production / Compose deployment | Out of scope (P8.1) | Environment variables, no secrets in the repository |

- **D1 – PostgreSQL version (proposal):** PostgreSQL **18**, pinned to the same major version in the dev container, Testcontainers image and CI.
- **D2 – Connection configuration:** The application reads `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME` and `SPRING_DATASOURCE_PASSWORD`. Defaults target the dev-container database and are dev-only credentials. No production credentials are committed.

### Schema ownership

- **D3 – One schema per bounded context (proposal):** `identity`, `groups`, `finance`, `files`, `notifications`. A context creates tables only in its own schema. Flyway's history table lives in a separate infrastructure schema (`flyway`). Infrastructure tables owned by other designs (for example the Spring Modulith event-publication registry, see [messaging](../../../stack/messaging.md)) receive their schema in their own task (P2.4).
- **D4 – No cross-context constraints:** No foreign key, view, trigger or cascade references a table in another context's schema. This is verified by an automated integration test (TC-5), not only by review.
- **D5 – Identifiers (proposal):** Entity primary keys and cross-context references use PostgreSQL `uuid`. IDs are **generated by the application** (UUIDv7 preferred: time-ordered, good index locality, known before insert and therefore usable in events and idempotency keys). The concrete generator (Hibernate `@UuidGenerator` style or a small library) is selected and verified in the plan. Finance revision-row keys are decided with P3.4/P4.

### Migrations

- **D6 – Single Flyway history in the modulith:** One Flyway configuration applies all migrations in version order at application startup. Extracted services later receive their own history.
- **D7 – Layout and naming (proposal):** `src/main/resources/db/migration/<context>/V<yyyyMMddHHmm>__<context>_<description>.sql`, for example `db/migration/groups/V202611051200__groups_create_group_tables.sql`. Timestamp versions avoid number collisions between parallel branches. A migration that is older than the newest migration on `main` at merge time is re-timestamped before merge; `outOfOrder` stays disabled.
- **D8 – Applied migrations are immutable:** Changes are new migrations. Flyway's checksum validation runs on every startup.
- **D9 – Baseline migration:** The first migration only creates the five context schemas. Business tables are introduced by the feature slices that own them (P2.x and later), not as placeholders.

### Hibernate / JPA

- **D10 – Schema validation only:** `spring.jpa.hibernate.ddl-auto=validate`. Hibernate never creates or alters tables. JPA mappings declare schema and table explicitly.
- **D11 – Open session in view disabled:** `spring.jpa.open-in-view=false`, so no database access happens during view rendering and transaction boundaries stay with the application layer (prerequisite for P1.3).

### jOOQ

- **D12 – jOOQ deferred (proposal):** P1.2 does not add jOOQ. Following the Phase 0 gate rule (*"no new framework is added solely for scaffolding"*), jOOQ and its code-generation workflow are introduced with the first adapter that needs SQL-centric access (expected in Finance, P3/P4). The persistence architecture's codegen requirements (pinned versions, offline compilation, CI freshness check) apply then.

### Tests

- **D13 – Test split:** `./mvnw test` runs only unit tests and requires neither Docker nor PostgreSQL. Integration tests are named `*IT`, run in `./mvnw verify` (Maven Failsafe) and require real PostgreSQL. The starter's `ShareWiseApplicationTests` context-load test becomes an integration test.
- **D14 – Reusable integration fixture:** One shared test fixture (annotation or base configuration) provides the PostgreSQL connection for all future persistence adapter tests. It starts a PostgreSQL 18 Testcontainer unless an external JDBC URL is configured.
- **D15 – No silent fallback:** If PostgreSQL is unavailable, integration tests fail with a clear message. They never pass via H2 or mocks.
- **D16 – Docker access in the dev container:** The dev container receives Docker access (for example the `docker-outside-of-docker` Dev Container feature) so Testcontainers works there. Alternatively, integration tests use the compose database through D14's external-URL option.

### Dependencies and tooling

- Remove `h2` and `spring-boot-h2console`. Add the PostgreSQL JDBC driver, Flyway (core + PostgreSQL module) and Testcontainers PostgreSQL (test scope). Exact artifact names and versions follow the Spring Boot 4.1 dependency management and are confirmed in the plan.
- Because `pom.xml` changes, the **offline dependency handoff** is regenerated and re-verified (`scripts/create-offline-handoff.sh pack`), coordinated with the handoff maintainer.

## Scope

**In scope:** D1–D16; dev-container PostgreSQL; datasource, Flyway and Hibernate configuration; baseline schema migration; integration-test fixture and initial integration tests; CI execution of integration tests; documentation updates (development guide, persistence architecture, stack overview status, backlog).

**Out of scope:** jOOQ (D12); the `Transactions`/`TransactionSession` abstraction (P1.3); business tables and adapters (feature slices); event-publication registry (P2.4); production roles, privileges, backups and full Compose/Nginx deployment (P8.x); financial history representation (P3.4/P4).

## Invariants

1. The application never starts with a schema that differs from the applied migrations for mapped entities (Hibernate validation, Flyway validation).
2. Every context's tables live in exactly one context-owned schema; no database object couples two context schemas.
3. Unit tests are executable without Docker, PostgreSQL or network access.
4. Integration tests either run against real PostgreSQL 18 or fail visibly.
5. Applied migrations are never edited.

## Failure behavior

| Situation | Expected behavior |
| --- | --- |
| Database unreachable at startup | Application startup fails with a datasource connection error; no fallback database |
| Pending migration fails | Startup fails; Flyway reports the failing script; PostgreSQL rolls back the failed migration's DDL transaction |
| Applied migration was edited | Startup fails on Flyway checksum validation |
| JPA mapping does not match schema | Startup fails on Hibernate schema validation |
| Docker / PostgreSQL unavailable for integration tests | `./mvnw verify` fails with a missing-infrastructure message; `./mvnw test` still passes |

## Acceptance criteria and test cases

| ID | Type | Setup | Action | Expected result |
| --- | --- | --- | --- | --- |
| TC-1 | Manual E2E | Fresh dev container (rebuild) | Start backend and frontend, open `/greetings` | App starts against PostgreSQL, Flyway applies the baseline, greeting flow works |
| TC-2 | Build | Machine without Docker / PostgreSQL | `./mvnw test` | Succeeds |
| TC-3 | Integration | Empty PostgreSQL 18 | Run migrations through the fixture | All migrations apply; schemas `identity`, `groups`, `finance`, `files`, `notifications` and the Flyway history exist |
| TC-4 | Integration | Migrated database | Application context starts with `ddl-auto=validate` | Context loads (replaces the starter context-load test) |
| TC-5 | Integration | Migrated database | Query `pg_constraint` for foreign keys whose referencing and referenced tables are in different schemas | Result is empty |
| TC-6 | Integration | No reachable PostgreSQL / Docker | `./mvnw verify` | Fails with a clear infrastructure message, not a pass |
| TC-7 | Build | — | `./mvnw dependency:tree` | Contains no `h2` artifact |
| TC-8 | CI | Merge request pipeline | Run backend job | Unit and integration tests run and pass against PostgreSQL 18 |
| TC-9 | Manual | Dev container with applied baseline | Edit the applied baseline migration locally, restart backend | Startup fails on checksum validation (then revert) |
