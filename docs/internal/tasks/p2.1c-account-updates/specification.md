# P2.1c - Account profile and password changes

**Status:** Approved specification; P2.1b is merged and the P2.1c profile and password-change implementation is integrated. Automated MR CI is reported green; final independent review and full manual-acceptance evidence remain tracked in the [plan](plan.md) and [acceptance record](acceptance.md).

## Goal and MVP boundary

An authenticated ShareWise user can inspect their own account, set or clear an optional display name, and change their password after confirming the current password. A successful password change retains the session that authorized the operation and revokes **all other sessions belonging to that account**. A single authenticated **Account** page provides both operations, using the existing frontend identity and HTTP infrastructure.

This is the reduced P2.1c MVP scope. It does not include email changes or verification, password recovery, self-service disablement/reactivation, explicit session/device management or independent "sign out other sessions" controls, arbitrary profile settings, or permanent account deletion (P2.1e). The existing `identity.users.disabled_at` is retained for IAM administrative state and is not exposed as a user operation. No IAM-to-Group profile projection or account-lifecycle event is introduced; Group display-name consumption, if needed, is separately designed with its owning context.

The architectural foundations are [P2.1a registration/login](../p2.1a-registration-auth/specification.md), [P2.1b session lifecycle](../p2.1b-session-lifecycle/specification.md), the [Phase 2 ER/integration handoff](../../integration/phase-2-foundation.md), [identity verification](../../../architecture/verified-credentials.md), [security](../../../stack/security.md), [transactions](../../../architecture/transactions.md), [persistence](../../../architecture/persistence.md), and [frontend architecture](../../../architecture/frontend.md). Follow the [human-reviewed development workflow](../../../development/ai-development-workflow.md) and [test architecture](../../../architecture/tests.md). P2.1b is **implemented and merged**; Phase D uses its actual session rotation, logout and persistence contracts.

## Architecture and data flow

IAM owns accounts, credentials, session records and the optional profile. All three account and password endpoints admit only a **verified primary IAM bearer** through the existing application-owned Spring Security chain and the trusted operation ingress. IAM operation-scoped services obtain the caller's own user ID from `IdentityContext`, never a client-provided account ID. Password change additionally obtains the canonical session UUID from the same primary evidence through `IdentityContext.requireSessionId()`, rather than from a request body or refresh cookie. This `sid` is checked against IAM's authoritative session record before a credential mutation. None of these operations authenticates using the refresh cookie.

The application services return narrow immutable account projections and typed outcomes. IAM-private jOOQ adapters access IAM tables through `JooqAccess` within `Transactions.execute(...)`; HTTP controllers own request mapping and RFC 9457 responses. They do not accept `SecurityContextHolder`, raw JWTs or servlet cookies as application inputs. Existing `CredentialEncoder` and `PasswordPolicy` are the only password hashing and validation mechanisms; there is no duplicate credential store or independently introduced session manager. The frontend Account route uses `core/identity` for account-specific HTTP and auth behavior and shared `lib/api` for transport, 401 recovery and response classification. Components do not independently refresh credentials or synchronize cookies.

### Profile storage and behavior

A reviewed Flyway migration adds `identity.user_profiles` in accordance with the Phase 2 ER: `user_id uuid PRIMARY KEY REFERENCES identity.users(id)` and nullable `display_name text`. Registration is **not** modified to create a profile row. No row and a row with `display_name IS NULL` have the same externally visible meaning: an unset display name. A profile update may insert the row on first use or update the existing row, with PostgreSQL's primary-key constraint arbitrating concurrent first writes. Concurrent valid updates use last-committed-write semantics; no profile versioning or lost-update warning is required for the MVP. A clear sets `display_name` to `NULL`; physical deletion of the profile row is unnecessary. No duplicate profile rows or cross-context access are permitted.

The profile response contains the authoritative user ID, registered email (read-only), and nullable display name; it contains no password verifier, session list, refresh metadata or secret. `displayName: null` means unset in the response. Profile updates use the explicit `clear` flag, with `clear == true` if and only if `displayName == null`; both fields are required and contradictory combinations are rejected. For MVP, a supplied non-null display name is 1–80 Unicode scalar values, must contain a non-whitespace character, and may not contain unpaired UTF-16 surrogates, C0/C1 controls, or Unicode line separators. Preserve allowed text exactly: do not change case, normalize Unicode or silently truncate it. The server is authoritative; frontend validation follows the same rule. Render display names as untrusted, escaped text, never as HTML or authorization identifiers. Clearing requires `{ "displayName": null, "clear": true }`; setting requires `{ "displayName": "Name", "clear": false }`. The 80-character cap is an **approved product limit**, not a requirement inferred from the ER's `text` column.

Profile reads/updates use the verified bearer identity and resolve only that user's account. Missing or disabled accounts are rejected, and an operation cannot address another account. As with other P2.1.0 bearer-authorized APIs, this slice does **not** promise immediate rejection of a valid stateless JWT merely because its underlying session was revoked: current-session eligibility for published consumers belongs to P2.1d. Password changes impose a stricter IAM-private live-session check because they alter credentials and session state. A separate global introspection layer is not introduced for profile editing.

### Password change and session effects

`ChangePassword(currentPassword, newPassword)` requires a verified primary IAM user **and session**. The operation checks that the account exists, is enabled, and the presented `sid` identifies an active, unrevoked, unexpired session owned by that user, using the same expiry rules as P2.1b. A refresh cookie, even if present, is irrelevant to this decision and cannot select a different account or session. A successful change retains precisely the current session and revokes all other active sessions of the account, including their ability to refresh. The current session's refresh generation, deadlines and `sid` remain unchanged; the API issues no replacement JWT or refresh cookie.

The current password is checked against an account snapshot **outside the long-held write transaction** using P2.1a's fixed PBKDF2-HMAC-SHA256 encoder. Validate the new password with `PasswordPolicy.validateRegistration` (8–256 UTF-16 code units, valid surrogate pairs, no normalization); reject a new password equal to the supplied current password. Compute the new encoded verifier before acquiring write locks. In one physical transaction, serialize against the account row, re-read the authoritative verifier/account status, reject a stale snapshot, verify current-session eligibility and update the password verifier together with revocation of every **other** session. Never commit the password without its required revocations, nor revoke sessions after a rejected password change. The operation returns success only after the transaction confirms commit; if commit or response delivery is uncertain, the caller must not blindly repeat the mutation.

Incorrect current passwords are rejected without changing the stored verifier or revoking sessions. Reuse P2.1a's existing account-level failed-attempt/lockout policy rather than installing an unthrottled, parallel password-guessing entry point: an incorrect current password updates that account's counter and potentially lockout in an intentional committed denial; success clears the failure state. The same lockout policy applies to password-change admission. The precise counter/lock behavior is an **explicit P2.1c policy addition**, not a pre-existing endpoint guarantee. Verify the initially read password verifier again under the account lock so password changes cannot overwrite one another or race successfully with login on a stale verifier. A changed verifier requires a new authenticated attempt, not automatic re-verification under a held lock.

The merged P2.1b session lock/adapter contract governs the multi-session update. Password change, refresh and logout must have a **documented shared lock acquisition order** and must recheck eligibility after their relevant locks, avoiding deadlocks, renewal of a revoked session, or sessions created by a concurrent login escaping the chosen revocation boundary. A serialization rule is required: a login/refresh committed before the password change's serialization point is subject to revocation as appropriate; a login after that point may succeed **only with the new password**. The backend owns the race outcome; browser coordination is not a concurrency substitute. In the merged P2.1b implementation refresh/logout lock the session first, then read account disablement without an account write lock; login locks the account before session creation. Password change locks the account first, then its caller session, then updates other sessions in the same transaction. PostgreSQL concurrency tests must establish the resulting serialization guarantees.

Session invalidation here means **loss of further refresh eligibility**, not instant invalidation of already issued stateless access JWTs. Those JWTs may be admitted until expiry under P2.1.0; P2.1d may later offer more authoritative state checks. The password-change API does not implement that broader introspection feature.

### HTTP and browser contract

Account profile routes are rooted at `/api/iam/v1/account`; password changes use `POST /api/iam/v1/auth/password`. All three require a verified primary IAM bearer and use RFC 9457 problem responses with stable `code` values and `Cache-Control: no-store`. `PATCH /account` modifies only the mutable part of the account representation, leaving its read-only ID and email unchanged; setting or clearing a display name is an idempotent state update. `POST /auth/password` is a credential-change command, not an account-representation patch.

The `/auth/password` path deliberately shares the authentication namespace with P2.1a/P2.1b, **but not the cookie-authentication policy**. The existing IAM security chain currently applies CSRF and exact-Origin checks to every unsafe `/api/iam/v1/auth/**` request. Introduce a narrowly scoped exemption for **exactly `POST /api/iam/v1/auth/password`** from that *cookie-backed* CSRF/Origin matcher while still enforcing primary-bearer authentication before dispatch. Do not weaken fail-closed protection for other current or future auth mutations or accept a refresh cookie in lieu of a bearer. No CSRF bootstrap, refresh-cookie rotation, or cookie issuance is part of password change. Keep the ordinary same-origin deployment and API request policies; extend the existing security chain rather than registering a competing filter chain. On the frontend, exempt only the cookie-backed `/auth/refresh` and `/auth/logout` operations from normal bearer injection; `/auth/password` must retain bearer injection and the usual pre-dispatch error classification, without automatic replay after dispatch or an uncertain response.

| Method and route | Request | Successful response | Defined failures |
| --- | --- | --- | --- |
| `GET /api/iam/v1/account` | Verified primary IAM JWT | `200 { "userId": "<uuid>", "email": "...", "displayName": null }` | `401` missing/invalid bearer; `403 account_unavailable` for missing/disabled account |
| `PATCH /api/iam/v1/account` | `{ "displayName": "Name", "clear": false }` or `{ "displayName": null, "clear": true }` | `200` with the complete account projection | `400 malformed_request` for malformed/missing fields, `400 validation_failed` for inconsistent or invalid values; bearer denial or `403 account_unavailable` |
| `POST /api/iam/v1/auth/password` | `{ "currentPassword": "...", "newPassword": "..." }` | `204` empty body, no new token/cookie | `400 validation_failed`, `400 current_password_invalid` (also active lockout), `409 credential_changed`, `403 account_unavailable`, or `401 session_unavailable` as applicable |

No account update allows an email/user ID field in the request. The backend JSON mapper rejects unknown request fields and scalar type coercions globally. Authentication ingress retains its existing `401 authentication_required`/`invalid_credential` behavior; a *post-dispatch* `session_unavailable` is **not** an eligible automatic-token-refresh signal under P2.1b's positive allowlist. Invalid input, bad credentials, disabled account, invalid session and concurrent updates must have no unintended credential or session mutations. Current passwords and verifiers never appear in problem details, logs, state inspection output or analytics.

The authenticated `/app/account` page sits in the workspace shell, reachable through its existing account menu and usable after P2.1b's lazy restoration. The shared `/app` layout guards all workspace routes rather than only account operations; terminal reauthentication redirects to login with a validated same-origin `next` path, while recoverable restoration failures and cross-tab context changes retain distinct retry/reload UI. This is a presentation gate, not a replacement for backend bearer authorization. It displays read-only email, editable display name, and a separate password form with current and new password fields. Changes are initiated explicitly; neither password fields nor their values are persisted in browser storage or cross-tab messages. For password changes, the form handles validation failures locally, clears sensitive inputs after success, and explains that **other sessions must sign in again**. It retains the current tab's auth state. A tab whose P2.1b coordinator reports a changed browser session suspends account actions instead of submitting under an unexpectedly changed context; ordinary in-memory JWT identity remains the backend authority for requests. Unknown password-change outcomes are reported as uncertain with an explicit sign-in/verification recovery path, not automatically retried. A revoked other session eventually reaches P2.1b's existing reauthentication UX on renewal; its already-issued access JWT has the documented bounded lifetime.

## Requirements and invariants

| ID | Requirement |
| --- | --- |
| IAM-C01 | Only a verified primary IAM bearer identifies the account. All profile and credential operations are scoped to its server-derived user ID; password change also verifies the bearer-derived session ID against authoritative IAM state. |
| IAM-C02 | `identity.user_profiles` is optional and one-to-one; absent profile and null display name are equivalent. Profile writes and concurrent first insertion cannot create duplicates or modify other users. |
| IAM-C03 | Profile input has the reviewed bounded Unicode/control policy; only `displayName` is mutable, `null` clears it, and reads never expose credential/session secrets. |
| IAM-C04 | Password changes require the current password and P2.1a's existing new-password validation, PBKDF2 encoder and lockout policy. A stale verified snapshot, disabled/locked account or ineligible session cannot change credentials. |
| IAM-C05 | Password verifier change and revocation of every *other* session commit in one physical transaction. The authorized current session and its refresh generation remain eligible and unchanged. |
| IAM-C06 | Refresh, logout, login and password change have consistent serialization and post-lock checks; no refresh is committed for a session revoked by an earlier password change, and no successful old-password login is committed afterward. |
| IAM-C07 | Expected denials have defined state effects; wrong current passwords can commit existing lockout counters but never mutate verifiers/sessions. Concurrency and unknown commit results cannot be reported as unqualified success. |
| IAM-C08 | Routes use established bearer ingress, IAM-private persistence, non-cached responses, stable problem codes and a single frontend account/API boundary; no cookie credential is accepted as bearer authority. |
| IAM-C09 | UI integrates with P2.1b's session-context states without inventing refresh/retry/cookie infrastructure; stateless access-token revocation limits are communicated accurately. |

## Central tests and acceptance

These cases prescribe the core observable properties; implementation phases add focused validation, mapping and component tests. PostgreSQL Integration/E2E tests must use real PostgreSQL 18 connections to establish locking, rollback and atomicity; fakes cannot satisfy those gates. Frontend mocks and a human HTTPS browser check cover distinct responsibilities.

| ID | Level | Scenario and required observation |
| --- | --- | --- |
| IAM-CT01 | Unit + HTTP | Anonymous/invalid JWT, wrong issuer/audience/type, or a caller attempting to supply another `userId`: no other account is read or changed; missing/wrong bearer follows the existing ingress contract. |
| IAM-CT02 | Unit + PostgreSQL E2E | Account without a profile: `GET` returns `displayName: null`; first `PATCH` creates a single owned row; clear returns to null and is repeatable. |
| IAM-CT03 | Unit + PostgreSQL Integration/E2E | Two concurrent first profile updates, invalid Unicode/overlong/control/blank values, escaped markup-like names, unknown fields and missing/disabled accounts: no duplicates, unexpected side effects or leaked data. |
| IAM-CT04 | Unit + HTTP | New password respects 8–256 UTF-16 units and surrogate rules; equal current/new rejected; wrong current password returns the agreed field/credential outcome without verifier/session mutation, while attempted guesses obey existing lockout behavior. |
| IAM-CT05 | PostgreSQL E2E + HTTP | Two active sessions for one user; valid current-password change preserves caller's session and its current refresh generation, updates the verifier and revokes only the other session(s); new login accepts only the new password. |
| IAM-CT06 | PostgreSQL E2E | Two simultaneous password changes, password change versus old-password login, and change versus refresh/logout on independent connections: deterministic winner/serial outcome, no stale overwrite, deadlock or partial revocation. |
| IAM-CT07 | PostgreSQL E2E | Disabled/locked account, revoked/expired/wrong-owner bearer session, induced verifier-update/revocation/commit failure: no accepted credential mutation or partial commit; no result claims success before commit. |
| IAM-CT08 | HTTP E2E | Real security chain enforces bearer-only account and password routes, body validation, correct `no-store`/ProblemDetail, and post-dispatch denial codes do not masquerade as pre-dispatch refreshable 401s. `POST /auth/password` requires a bearer without cookie CSRF bootstrap; other unsafe `/auth/**` operations keep their existing CSRF/Origin protection, and cookie alone is insufficient. |
| IAM-CT09 | Frontend Vitest + component | Profile load/set/clear, disabled submit during in-flight actions, password errors, sensitive-input clearing, lost-response uncertainty and session-context-change prompt; use the existing shared API and mocked identity transport. |
| IAM-CT10 | Human HTTPS browser | Login, visit `/app/account`, change/clear name, change password, verify current tab continues and second browser profile cannot refresh, check wrong-password and account-switch UX, re-login with new password; inspect cookie attributes without revealing their values. |

## Integration gates and intentional deferrals

Profile phases A–C and the Phase D password service have been accepted. The password endpoint, Account security form and workspace-wide authentication guard are integrated for Phase E review. Protected-operation P2.1b browser scenarios belong to P2.1c's general manual acceptance; the earlier P2.1b smoke test alone does not establish their completion.

The Phase A profile migration and maintainer-regenerated IAM jOOQ schema are integrated and accepted. Future schema changes still require the reviewed PostgreSQL migration and generated-source handoff; Phase D does not require a migration.

Out of scope are account disablement/reactivation UI, session/device listings or direct revocation controls, email changes, password reset/recovery, security notification emails, profile synchronization into Group Management, automatic reauthentication of revoked sessions, and P2.1e deletion. The existing P2.1b refresh history/replay rules and P2.1d's optional authoritative eligibility for other modules remain separately owned. Future requirements must pass their own specification gate rather than accumulating in the MVP.

The human first approves the specification, then the [phased plan](plan.md). Each phase produces a reviewable patch, runs available checks and pauses for approval. PostgreSQL/HTTP/browser acceptance and independent security review are mandatory before final merge authorization.
