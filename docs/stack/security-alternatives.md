# Identity and authorization alternatives

**Status:** Supporting rationale for the [preliminary security architecture](security.md). The selected direction combines application-owned IAM sessions and rotating refresh tokens, Spring Security primitives, short-lived signed identity JWTs, and issuer-qualified domain attestations. The deployment target is a statically served frontend behind a reverse proxy.

| Alternative | Why it was not selected as the default |
| --- | --- |
| ASP.NET Core Identity-style framework-managed account system | Spring Security provides password, authentication and authorization infrastructure plus simple JDBC user management, but not the complete opinionated account/refresh-session workflow ShareWise requires. The selected design uses framework primitives with an application-owned account model and orchestration. |
| Keycloak or a full external identity provider | Valid option for a larger system, but adds another deployable and configuration lifecycle while IAM itself is a project bounded context. Revisit if standards-based federation or account-management requirements warrant it. |
| Full OAuth/OIDC authorization server from the outset | Offers standardized issuance/grants but adds protocol/client machinery beyond the initial first-party login/refresh flow. The selected workflow uses Spring's security and JOSE components. Authorization-server capabilities or RFC 8693 token exchange remain options if interoperable clients become necessary. |
| Server-side browser sessions for every API request | Make immediate session revocation straightforward but introduce an online shared session dependency into every extracted service. Short-lived bearer identity tokens provide independent local validation. Online introspection remains an optional later extension for stricter freshness requirements. |
| Group roles and memberships inside IAM access JWTs | IAM does not own those facts; copied claims become stale and introduce cross-context coupling. Domain authorities issue scoped attestations from authoritative state. |
| Event-replicated authorization state as the default | Replication lag cannot bound revocation latency reliably. Permission issuance relies on each authority's current state and JWT expiry bounds stale credentials. Optional event-driven, service-local revocation state may reject tokens earlier, but is not a prerequisite for authorization correctness. |
| Synchronous authorization check for every domain request | Gives fresher information but couples availability and latency to another context, particularly after service extraction. Bounded-life attestations cover normal requests; selective online verification can be introduced for operations with stricter freshness requirements. |
| Custom token format or unconstrained multi-level delegation | Unnecessary parsing, signing and trust complexity. The selected protocol uses signed JWT/JWS profiles with a strict two-level IAM-to-domain hierarchy. A token exchange standard can be evaluated separately. |
| Server-rendered Next.js application or BFF | Adds an application server to the browser request path without a current requirement for server rendering or server-managed browser sessions. Static asset hosting with Nginx and same-origin `/api/*` routing is sufficient for the selected bearer-token and refresh-cookie model. |

The [generic File Management ACL proposal](../file-management-acl-proposal.md) explores an optional consumer of the common attestation trust model. That ACL design remains a separate choice. Token transport headers, access-token and attestation lifetimes, signing algorithms, cookie CSRF mechanism, and operational key management require implementation validation.
